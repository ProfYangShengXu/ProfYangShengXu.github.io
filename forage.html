forage

Technical Retrieval

技术文档爬虫与中文改写召回。中文 query 展开成多路英文检索，加权融合后返回带出处的父块。

GitHubSOURCE

是什么

一个面向技术博客的检索层。它负责两件事：把技术博客的内容增量抓取入库； 把中文提问扩展成多路英文检索，融合后返回最相关的原文段落。

做什么

爬取官方 feed/API 拿到文章正文并入库（内容未变则跳过向量计算）； 对中文 query 做改写扩展，走多路检索并用加权 RRF 融合，返回父块原文； 支持 explain 回答「这条为什么排在前面 / 那条为什么没进来」； 支持在冻结的标注集上量 Recall / MRR / NDCG。

为什么这么做

中文的检索需求和技术博客的英文原文之间存在词面鸿沟 —— 用中文直接检索英文语料， 词面匹配基本失效，纯向量检索又容易在专有名词上翻车。所以把中文 query 改写成多路英文表达， 每一路各自检索，再用 RRF 做无监督融合：不依赖任何一路的打分校准，只看名次。

另一个决定是不自己做检索层，直接复用已有的记忆层（BM25 + 向量 + 精排 + 父子块）。 检索这块已经被反复验证过，重复实现只会得到两个都需要维护的版本。 forage 只做增量的事：爬虫、改写、可解释、可评测。

边界也划得很清楚：负责把相关段落找出来，不负责判断这些段落该不该采信。 生成和判断交给上层调用它的 agent —— 检索层的职责越单一，替换和评测越容易。

案例

中文提问召回英文原文多路改写 + 加权 RRF

用中文提一个技术问题，系统不直接检索，而是先展开成若干条英文表达：

中文 query
  ↓ 多路改写
path 1 原 query（阻尼）
path 2..n 英文改写表达
  ↓ 各路独立检索 + 加权 RRF 融合
父块原文（带来源、带时间）

融合不用分数而用名次，是为了避开不同检索路径分值尺度不一致的问题 —— 向量相似度和 BM25 分数本来就没有可比性。名次融合不需要校准，也不怕某一路失效。

为什么它没进来explain 子命令

检索系统最难调试的地方不是"结果不好"，而是"不知道为什么不 good"。 所以提供 explain：给一个 query 和一个文档名，回答这篇为什么排在当前位次、 或者为什么根本没能进入结果集。

这一条是把检索从「调参数试运气」变成「可以定位问题」的关键。
